## The Tauri client builds, and the CSP change compiles

`npm run tauri build` failed twice before succeeding, and the reason matters
because it is **not** a defect in this branch:

```
failed to read plugin permissions: failed to read file
'\\?\C:\Users\jpegg\code\necesse-server-gui\client\src-tauri\target\release\build\
tauri-4e690c6ec17d5313\out\permissions\app\autogenerated\commands\app_hide.toml':
The system cannot find the path specified. (os error 3)
```

The path in that error is `necesse-server-gui\...`, which is not where this
repository lives (`necesse-projects\server-gui\...`). The repository was moved
at some point and Cargo's build cache under `client/src-tauri/target/` had the
old absolute path baked into a build script's recorded `OUT_DIR`. No tracked
file references the old path, and the old directory no longer exists, so this
is purely stale local cache. `cargo clean -p tauri -p tauri-app` did **not**
clear it; deleting `client/src-tauri/target/` entirely did.

A CI runner does a fresh checkout with no cache, so this cannot happen there.
It will happen to any contributor who moves or renames their checkout, and the
fix is to delete `client/src-tauri/target/`.

After the clean, the build succeeded in 1m13s:

```
Finished `release` profile [optimized] target(s) in 1m 13s
   Built application at: ...\target\release\NecesseServerManager.exe
Finished 2 bundles at:
    ...\target\release\bundle\msi\Necesse Server GUI_0.1.0_x64_en-US.msi
    ...\target\release\bundle\nsis\Necesse Server GUI_0.1.0_x64-setup.exe
```

Two things this settles with evidence rather than reasoning:

- **The CSP change compiles.** `connect-src 'self' http: https: ws: wss:` is
  accepted by the bundler. What it does at runtime in a real WebView is still
  not verified — nobody has launched the installed app and watched a request to
  a user-typed host succeed.
- **The installer filenames really do come from `productName`, not
  `mainBinaryName`.** The binary is `NecesseServerManager.exe`; the installers
  are `Necesse Server GUI_0.1.0_x64-setup.exe` and
  `Necesse Server GUI_0.1.0_x64_en-US.msi`, with spaces. The release workflow
  globs `bundle/nsis/*.exe` and `bundle/msi/*.msi`, and both files landed in
  exactly those folders, so the globs will match. The earlier conclusion that
  the folder names are fixed constants unrelated to `productName` is confirmed.

## The setup wizard runs end to end, and one real limitation was found

The wizard was driven to completion against the staged build with a scratch
`NECESSE_MANAGER_DATA` and a synthetic game install (a `Necesse` data directory
with `mods` and `saves\worlds`, a server root holding `Server.jar` and
`jre\bin\java.exe`, and a `steamcmd.exe`). All five path answers were accepted
with an `OK:` confirmation, the port was recorded, and the wizard ended on its
success branch rather than its "not usable as it stands" branch — meaning its
own closing `configProblems` check passed.

**The limitation, which is a real finding:** the wizard cannot be driven by
piping a file into it. `readline/promises` over a non-TTY stdin delivers the
first line and drops the rest, and the process then exits with Node's
`Detected unsettled top-level await` warning after answering exactly one
question, having written nothing:

```
Where is the game's data directory? ...
>   OK: ...\scratchpad\game\Necesse
Where is the dedicated server installed? [C:\necesseserver]
Warning: Detected unsettled top-level await at .../dist/setup-cli.js:91
```

An interactive operator at a terminal is unaffected. What this rules out is
`setup.cmd < answers.txt`, and any attempt to script the wizard
non-interactively. It fails visibly rather than writing a half-formed config,
which is the acceptable failure mode, but it is worth knowing before anyone
tries to automate a first-run. Verification here used a driver that waits for
each `> ` prompt before writing the next answer, the way a person does.

## The legacy-state refusal, and the trap it could have set for itself

A pre-move state file (`mods.json`) was placed beside `dist/` with an empty
state directory, which is the shape of the one existing production install.

| Check | Result |
|---|---|
| Boot refuses | exit 1 |
| Refusal names `migrate.cmd` | yes |
| Refusal written to a durable file | `boot-refusal.txt` in the state dir |
| **Second boot still refuses** | exit 1 |
| `migrate-cli` exits 0 | yes |
| `mods.json` copied into the state dir | yes |
| Original left in place (copy, not move) | yes |
| Boot after migration stops naming `migrate.cmd` | yes |
| Boot after migration asks for setup instead | yes |

The fourth row is the one worth pausing on. The refusal writes its own log
*into the state directory*, and the daemon decides whether a legacy install
still needs migrating by asking whether that directory is empty. Had the
refusal log counted as content, the second boot would have concluded the
migration had already happened and started against an empty state directory —
turning a safe refusal into the silent data-loss path the refusal exists to
prevent. It does not, and now there is direct evidence rather than a unit test
of the predicate.
