1. Goal & scope

The daemon and client currently work for exactly one machine. The server's identity is compiled into both halves: daemon/src/config.ts defaults to one person's paths, client/src/useDaemon.ts hardcodes http://192.168.1.106:8710, and the Tauri CSP whitelists that single origin so no other one can be reached at runtime. Anyone else cannot use the software without editing and rebuilding both packages.

This work makes the daemon's location and run mode configuration rather than source, gives the client a runtime connection screen, adds authentication because the daemon spawns processes, and publishes the result as a GitHub repository with prebuilt release artifacts. A user should be able to download two files, run a setup wizard, and be managing their own server without a toolchain.

The target audience is someone running a Necesse dedicated server on a Windows box on their own LAN. Third-party hosting is not a goal; the repository being public is what lets anyone who wants that adapt it.

3. Daemon: configuration model

Derived directories

The game is launched with -datadir, and derives its mods and worlds folders from it. The daemon reads and writes those same two folders directly. Today all three are literal strings in config.json and dataDirConflict refuses to boot when they disagree — a guard that exists only because three literals can disagree.

loadConfig will instead always compute modsDir and worldsDir from dataDir via the existing modsDirFor and worldsDirFor helpers, overwriting whatever the file said. saveConfig omits both keys, so a config the daemon writes cannot carry a stale copy.

The DaemonConfig type keeps both fields as required, so no consumer changes. Only the on-disk shape loses them:

export type StoredConfig = Omit<DaemonConfig, "modsDir" | "worldsDir">;

The drift guard is kept, not deleted. An existing config.json carrying the two legacy keys is checked against dataDir before anything else runs, and a disagreement still refuses to boot with today's message. Silently preferring the derived value would resolve real drift without telling anyone — and a person whose config drifted has a wrong belief about where their mods live, which they need to hear about. Once the daemon saves for any reason the legacy keys are dropped and the check has nothing left to fire on.

Defaults

DEFAULT_CONFIG loses every path. What survives is only what is universal to every installation:

Keeps a defaultHas no default — required
port 8710, jvmArgs, serverAppId, workshopAppId, stopTimeoutMs, modUploadMaxBytes, owners (empty), lastWorld (null), steamApiKey (empty), authToken (empty — see below), and modLibraryDir / modLibraryFile / modSetsFile, which are relative to DAEMON_DIR and therefore already portable dataDir, serverRoot, javaExe, serverJar, steamcmdExe

loadConfig no longer writes a config file when none exists. Today an absent file produces one full of the author's paths and a daemon that boots pointed at directories that do not exist on the user's machine. It throws instead:

No config.json in C:\necesse-daemon.
Run setup.cmd in that folder to create one.

New fields

FieldTypeMeaning
authTokenstring Shared secret every request must present. Always generated by setup, so no configuration the wizard produces is unauthenticated. Its default is nonetheless the empty string, which disables authentication: that is both the documented trusted-LAN opt-out and what makes an existing pre-token config.json keep working across the upgrade (§11). The empty value is therefore a deliberate choice, never a missing one.

PublicDaemonConfig must drop authToken the same way and for the same reason it drops steamApiKey: replaced by a boolean rather than redacted in place, so there is no shape in which the secret survives the trip.

export type PublicDaemonConfig =
  Omit<DaemonConfig, "steamApiKey" | "authToken"> & {
    steamApiKeyConfigured: boolean;
    authRequired: boolean;
  };

The doc comment on PublicDaemonConfig becomes false and must be rewritten. It currently reads “The API has no authentication by deliberate design, so every field it emits is readable by anything on the LAN.” Leaving that in place would tell the next reader the opposite of what the code does.

4. Daemon: setup wizard

daemon/src/setup.ts, run as npm run setup from source or setup.cmd from a release zip. Interactive, on the server box, by the human.

Being run interactively is the point, not an accident. The wizard reads process.env.APPDATA to propose dataDir. Run as the logged-in user that resolves to their real %APPDATA%\Necesse; the value is then frozen into config.json and passed to the game as -datadir. That is exactly what lets the daemon later run as SYSTEM, whose own %APPDATA% is C:\Windows\system32\config\systemprofile and holds no worlds at all.

Probe, propose, confirm

The wizard never guesses silently. For each value it shows what it found and where, and takes the found path as the default answer:

ValueProbed from
dataDir%APPDATA%\Necesse; existence of saves\worlds inside it is reported as confirmation
serverRoot, serverJarServer.jar under C:\necesseserver, then under Steam library steamapps\common folders
javaExe<serverRoot>\jre\bin\java.exe if present — the server ships its own JRE — otherwise java.exe on PATH
steamcmdExePATH, then C:\steamcmd, then %USERPROFILE%\steam
portDefaults to 8710; the wizard binds it briefly to check it is free and says so if it is not
authTokenGenerated, not asked: randomBytes(24).toString("base64url"). Printed at the end.
steamApiKeyAsked last, optional, explaining it is needed only for workshop search and where to get one

The probe logic is a pure function — candidate paths in, findings out — separate from the prompting, so it is testable without driving a terminal.

The wizard writes config.json without a BOM, refuses to overwrite an existing config unless told to, and finishes by printing the token and the exact next command (start-daemon.cmd, or register-task.ps1 for the scheduled task).

5. Daemon: boot validation

dataDirConflict's single call site in index.ts is replaced by configProblems(cfg), which returns every problem rather than the first, classified:

export interface ConfigProblem {
  key: keyof DaemonConfig;
  message: string;
  fatal: boolean;
}
SeverityConditionsBehaviour
Fatal Legacy modsDir/worldsDir disagreeing with dataDir; dataDir, serverJar or javaExe missing from disk; any of the five required path fields absent or empty. Not authToken, whose empty value is meaningful. Print every fatal problem, then exit non-zero. The daemon never boots into a state where it would launch the game against the wrong tree.
Warning steamcmdExe not found Boot. Starting, stopping and world management do not need steamcmd; only mod installs and server updates do, and those already fail with the underlying error. The warning is logged and carried to the client so it surfaces before a user tries.

Warnings reach the client through StatusPayload.configWarnings: string[]. That payload is already documented as “the full picture a client needs” and is delivered on connect in the WebSocket backlog, so no extra request is needed and no polling is introduced.

6. Daemon: authentication

A Fastify preHandler requires Authorization: Bearer <token> on every route and answers 401 with a plain message when it is absent or wrong. The comparison uses timingSafeEqual over equal-length buffers.

The WebSocket upgrade cannot carry a header — browsers offer no way to set one on a handshake — so it reads ?token= from the query string and rejects the upgrade otherwise. Both paths consult the same check function; there is one implementation of "is this request authorized" and no second path to forget.

An empty authToken disables both checks. This is the documented opt-out for a trusted LAN and the reason an existing install keeps working across the upgrade (§11).

This is a shared secret over plain HTTP on a LAN, and the README will say so. It stops a careless or compromised device on the same network from starting processes on the server. It is not protection against someone who can read the traffic, and the daemon must still never be port-forwarded.

7. Client: connection settings

The CSP has to open

tauri.conf.json's connect-src currently names one origin. A Tauri CSP is baked at build time, so a user-typed host cannot be reached under it at all. It becomes:

connect-src 'self' http: https: ws: wss:

That is a genuine widening and is stated as such in the README. The alternative considered and rejected was proxying every daemon call through Rust to keep the CSP pinned: a large Rust surface plus a new client-to-Rust boundary that vitest could only mock, spent defending a webview that renders no untrusted HTML. img-src is unchanged and stays restricted to Steam's CDNs.

Settings module and screen

client/src/settings.ts wraps localStorage over { host, port, token }, with validation on read so corrupt or partial stored data produces "not configured" rather than a malformed URL.

A new ConnectionSettings component is the first screen when nothing is stored, and is reachable afterwards from a gear in ServerHeader. It offers:

  • Host, port and token fields.
  • Test connection, which reports what actually happened — unreachable, connection refused, 401 rejected, or connected — rather than a single generic failure. It succeeds on a 200 from GET /api/status; no new endpoint is added and no daemon version is claimed, because the daemon does not currently report one.
  • Copy and Paste for the {host, port, token} blob, so setting up a second workstation is a paste rather than retyping a 32-character token.

Threading the token

useDaemon.ts loses its DAEMON_BASE and WS_URL constants; both derive from settings. App.tsx's hardcoded “Connecting to the daemon at 192.168.1.106:8710” renders the configured host.

makeApi(base) becomes makeApi(base, token) and sets the bearer header on every request.

uploadMod builds its own fetch and will not inherit the header. It deliberately bypasses the shared request() helper because it sends a raw jar body rather than JSON. It is therefore the one call that would ship broken while every other action worked — the same shape of defect that once let five actions fail in production with 119 tests green. It gets the header explicitly and an integration test of its own.

A 401 is terminal

useDaemon retries the socket every 2 seconds. Against a rejected token that spins forever behind a "connecting" message that never resolves and never explains itself. A 401 from either channel therefore stops the retry loop and returns the user to the settings screen saying the token was rejected. Any other failure keeps today's retry behaviour, because a daemon that is merely down should be waited for.

Shared types

daemon/src/types.ts and client/src/types.ts must stay byte-identical. This work changes them (configWarnings, authRequired, ConfigProblem), so both are written in the same pass and hashed afterwards.

One thing must be verified rather than assumed before the repository is pushed public: that the Steam Web API key never landed in a commit. config.ts asserts it was deliberately kept out, but an assertion in a comment is not evidence. git log -S across the full history is, and it is a precondition of publishing, not a follow-up.

Where daemon state lives

State stays in the daemon's own directory next to dist/: config.json, mods.json, mod-library/, mod-library.json, mod-sets.json. Moving it to %PROGRAMDATA% was considered and rejected as churn against a layout the deploy script and every existing install already assume.

This makes "upgrade by deleting the folder and unzipping the new one" destructive. mod-library/ is the only copy of every hand-placed and uploaded jar, and mod-sets.json is the only record of what each world loads. The README's upgrade instruction is therefore explicit: replace dist/ and node_modules/, keep everything else. The release zip nests its replaceable content so the distinction is visible rather than a thing you had to have read.

Repository name

necesse-server-manager, matching the client binary name. The current folder name server-gui says nothing about what it manages.

9. Error handling

The existing rule is unchanged and extends to the new code: a missing file is distinguished from a real failure, and everything else rethrows with the path and the underlying message. A catch that returns a default is a defect here.

  • Boot refusal prints every fatal problem, not the first. A user fixing one path at a time across four restarts is a worse experience than one list.
  • Setup failures name the path they were writing and why it failed. A wizard that says "failed to save" has wasted the user's answers.
  • The client's Test connection distinguishes unreachable, refused, 401 and connected. These need four different fixes and a single "could not connect" hides which.
  • 401 responses carry a plain message, not an empty body. A user whose token is stale needs to read that fact, not infer it from a status code.

10. Testing

The project's rule is to cover the seam rather than each side of it. Authentication is a seam, and it is added to the one test that crosses it for real.

Integration client/test/api.integration.test.ts

This test stands up a real daemon on an ephemeral port and drives it with the real client transport. It gains a daemon configured with a token, and asserts:

  • Every mutating call succeeds with the correct token.
  • A wrong token and an absent token are both rejected with 401 over HTTP.
  • The same for the WebSocket upgrade, which uses a different mechanism (query parameter) and therefore proves nothing about itself from the HTTP result.
  • uploadMod specifically, because it is the one call that builds its own request and so is the one that can be broken while the suite is green.

Daemon unit tests

  • loadConfig throws naming the directory when the file is absent, and does not create one.
  • modsDir and worldsDir are derived from dataDir and ignore stored values; saveConfig omits both keys.
  • A legacy config whose stored dirs disagree with dataDir is still refused.
  • configProblems classifies fatal versus warning correctly and returns all problems rather than stopping at the first.
  • The setup probe function, over fixture directory layouts: server root found and not found, bundled JRE present and absent, steamcmd on PATH and absent.

Client unit tests

  • settings.ts round-trips, and treats corrupt or partial stored data as unconfigured rather than throwing.
  • The connection screen renders first when nothing is stored, and Test connection reports each of the four outcomes distinctly.
  • A 401 stops the reconnect loop and returns to settings; a network error does not.
  • Copy and paste of the connection blob round-trip.

11. Migrating the live install

The existing server has a config.json with all three directory keys, no authToken, and a running daemon. The upgrade path must not break it.

  1. An absent authToken reads as empty, which disables authentication. The upgraded daemon therefore keeps serving the existing client unchanged.
  2. The stored modsDir and worldsDir agree with dataDir today, so the back-compat guard passes and the derived values are identical. The first save drops the legacy keys.
  3. A token is adopted deliberately: add it to config.json with the daemon stopped, restart, then enter it in the client's settings screen.

The deploy scripts already copy dist/ and never remove anything, so the mod library and sets are untouched by the upgrade. As always, GET /api/status reporting stopped is the check before deploying, because the game server is a child process of the daemon.

12. Out of scope

  • LAN auto-discovery. Probing a subnet for open daemon ports is real work and reads as port scanning to some security software. The connection screen takes a typed address.
  • Linux or macOS daemon. Windows only, stated in the README.
  • A real Windows Service. The scheduled task covers the same ground without a third-party wrapper.
  • Editing daemon paths from the client. An unauthenticated-by-default LAN endpoint that rewrites the path of the executable the daemon spawns is a remote code execution primitive. Configuration stays server-side.
  • Code signing. The installer is unsigned and SmartScreen is documented.
  • Filtering Update All by workshop timestamp. mod-installer.ts's updateAll reinstalls every managed mod unconditionally; the time_updated comparison exists only as the badge behind GET /api/mods/updates. That is a real gap, but it is a behaviour change to mod management rather than to packaging, and it is tracked separately.
