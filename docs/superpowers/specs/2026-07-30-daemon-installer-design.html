1. Goal & scope

The daemon currently ships as a zip. Installing it means: unzip somewhere, install Node 22+ yourself, run setup.cmd, then run register-task.ps1 as Administrator, in that order, having read the README closely enough to know that the order matters. That is a reasonable amount to ask of someone who already runs a dedicated server, and too much to ask of everyone else.

This adds a second artifact: a single elevated installer that places the files, brings its own Node, runs the existing setup wizard, registers the scheduled task and firewall rule, and provides a real uninstaller. The zip stays exactly as it is.

2. Decisions taken

QuestionDecisionConsequence
Node runtimeBundle a private one Roughly 35MB larger. The install is genuinely self-contained and cannot be broken by the user upgrading or removing their own Node. Creates an ongoing duty to update it.
ConfigurationLaunch the existing wizard in a console No second implementation of path probing, validation or token generation. Costs a visible console window mid-install.
Uninstall and the state directoryNever touch it Uninstall cannot destroy a mod library. Leaves a directory behind that a user has to remove deliberately.
ToolchainInno Setup Readable script for a repo meant to be forked. Needs ISCC on the runner, installed via choco if absent.

3. Layout and the bundled runtime

Default install directory C:\Program Files\Necesse Server Manager ({autopf}). Administrator is required regardless, for the scheduled task and the firewall rule.

Contents are the release zip's, plus the runtime:

C:\Program Files\Necesse Server Manager\
  dist\
  node_modules\
  node\node.exe          <- pinned, private
  package.json
  setup.cmd
  start-daemon.cmd
  migrate.cmd
  register-task.ps1
  config.example.json

Program Files being read-only for the daemon is fine, and worth stating because it would otherwise look like a problem. Nothing writes into the install directory at runtime: config.json, mods.json, mod-sets.json, mod-library.json and mod-library\ all live in %PROGRAMDATA%\NecesseServerManager, and boot-refusal.txt is written there too. The install directory holds only code.

4. Shim and task changes

The three .cmd shims currently invoke a bare node, which resolves against PATH. They gain a preference for the bundled runtime with a fallback:

set "NODE=node"
if exist "%~dp0node\node.exe" set "NODE=%~dp0node\node.exe"
"%NODE%" dist\index.js %*

One set of shims then works in both artifacts: the installer, where the bundled runtime exists, and the zip, where it does not and the system Node is used exactly as today. Shipping two different sets of shims was rejected - they would drift.

register-task.ps1 gets the same preference, ahead of its existing Get-Command node.exe lookup and its C:\Program Files\nodejs\node.exe fallback. This matters more than it looks: the scheduled task stores the resolved path literally, so after this change the task points at a runtime that ships with the daemon and cannot be changed out from under it.

5. Install sequence

All in one elevated run:

  1. Quiesce any previous install. If the scheduled task exists and is Running, stop it and wait for it to exit and for the port to clear - the same two waits register-task.ps1 already performs, for the same reasons. Overwriting node\node.exe while it is running fails outright, and a surviving process keeps the port.
  2. Copy files.
  3. Run the setup wizard in a visible console window and wait for it to exit - unless config.json already exists in the state directory, in which case skip it entirely.
  4. Register the scheduled task and firewall rule, by running the shipped register-task.ps1 - but only if config.json now exists, and only if that task was selected.
  5. Report honestly. If the wizard was cancelled or failed, say so and point at the Start Menu shortcut, rather than finishing with a success page over a half-configured install.

Step 4's ordering is load-bearing, not stylistic. Registering the task before a config exists would start a daemon that refuses to boot (there is nothing to read), and register-task.ps1 ends with a health check against /api/status - so it would report failure on a registration that had in fact worked perfectly. The condition on config.json existing is what keeps the installer from producing that outcome.

Both post-install actions are Inno [Tasks], selected by default. That is a product-neutral choice with a useful side effect: /TASKS="" disables both, which is what makes a silent install testable (§9).

Start Menu shortcuts: Setup, Start daemon, Register boot task, Open state folder.

6. Upgrade

Inno recognises an existing install by AppId. An upgrade stops the task (step 1 above), replaces the files, and skips the wizard because config.json exists. An upgrade must never make someone re-answer five path questions, and must never regenerate their access token - that would silently lock out every client already configured with the old one.

Task handling on an upgrade follows what was already there, rather than what the checkbox happens to say. If the scheduled task existed before the upgrade it is re-registered afterwards, so it points at the new files, and left running. If it did not exist, the upgrade does not create one: someone who deliberately runs the daemon by hand should not find a boot task appearing because they accepted a default on an upgrade screen. The default state of that checkbox on an upgrade is therefore read from the machine, not assumed.

Upgrading from a zip install is documented, not automated. Someone whose state still sits beside dist\ in an old unzipped folder should run migrate.cmd in that folder before installing. The installer creates a fresh directory in Program Files and cannot know where they unzipped the old one, so its legacy-state check will find nothing and the install will look empty rather than broken. A README sentence is the honest fix; a filesystem search for old installs is not.

7. Uninstall

  1. Stop the scheduled task and wait for it to exit.
  2. Unregister the task.
  3. Remove the firewall rule.
  4. Delete the install directory.
  5. Leave %PROGRAMDATA%\NecesseServerManager entirely alone, and print its path so the user can remove it deliberately.

No "also remove my data" checkbox. It was considered and rejected. mod-library\ is the only copy of every uploaded and hand-placed jar, and uninstall is precisely the screen people click through without reading. This is the same stance the rest of the project already takes: migrate.cmd copies rather than moves, and the daemon refuses to boot rather than relocating state on its own.

8. Build and release

PathPurpose
installer/necesse-daemon.issThe Inno Setup script
installer/node-version.txtThe pinned Node version, as a single source of truth. The release workflow reads it to fetch the runtime, so bumping Node is one line in one file

The release workflow, after staging the daemon zip contents, downloads node-v<pinned>-win-x64.zip from nodejs.org, verifies its SHA-256 against the published SHASUMS256.txt, extracts node.exe to node\node.exe in the staging directory, then runs ISCC to produce necesse-daemon-vX.Y.Z-setup.exe and attaches it to the release.

The checksum step is not ceremony. This is a binary being shipped to other people under the maintainer's name. An unverified download is the one place a supply-chain problem could enter this project, and the verification costs three lines.

Release artifacts become four: the daemon zip (unchanged, still requires a system Node), the daemon installer, and the two client installers. The daemon installer is unsigned, like the client's, so SmartScreen will warn - documented in the README beside the existing client warning rather than discovered.

9. Verification

CI

ci.yml compiles the .iss with ISCC on every push. That alone catches a missing file, a wrong path or a syntax error - the failure modes that would otherwise appear for the first time at tag time, which is the worst moment to discover them.

Local, before release

A script that proves the artifact rather than inspecting it:

  1. Install with /VERYSILENT /DIR=<scratch> /TASKS="".
  2. Assert the files landed, including node\node.exe.
  3. Run the installed start-daemon.cmd against a scratch NECESSE_MANAGER_DATA, with node removed from PATH, and assert the daemon starts and answers. Removing it from PATH is the whole point: without that, a bundled runtime that was never actually used would pass identically.
  4. Run the uninstaller with /VERYSILENT and assert the install directory is gone and the state directory and its contents are intact.

Step 4 is the assertion that matters most in this document. It is the claim that would otherwise only ever be tested by a user losing their mod library.

Not testable silently

The interactive wizard launch and the real scheduled-task registration cannot be exercised by a silent install. Those get a real install on the live server, the same way the state-directory migration was verified, and whatever is not run gets recorded as not run.

10. Out of scope

  • Auto-detecting an old zip install to migrate from. Documented instead (§6).
  • Installer pages replacing the setup wizard. Rejected in favour of one implementation of config writing.
  • Code signing. Unsigned, SmartScreen documented.
  • Changes to 02-deploy.ps1. It remains the maintainer's fast dev loop and is unaffected.
  • Bundling Node into the zip. The zip stays as it is; the shim fallback covers it.
  • A client installer change of any kind. The client already ships an NSIS installer and an MSI from Tauri.
