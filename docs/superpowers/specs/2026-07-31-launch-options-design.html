1. Goal, and the bug that prompted it

The daemon launches the game with a fixed command line. Everything except the world name is baked into config.json and applies to every world equally, so there is no way to give one world a different player cap, message of the day, password, or owner without hand-editing a file on the server and restarting.

This started as a live bug, not a feature request. buildArgs emits one -owner per entry in config.json's owners array. But GameLaunch.parseLaunchOptions accumulates into a HashMap<String, String> and calls out.put(option, value), so a repeated flag overwrites rather than appending, and ServerLoader then reads a single value:

String owner = GameLaunch.launchOptions.getOrDefault("owner", null);
Settings.serverOwnerName = owner;

Necesse supports exactly one owner. With owners: ["Jeff", "Eli"] the server has been applying Eli only, silently, since the feature was written. DaemonConfig.owners: string[] models a capability the game does not have, and that mismatch is what produced the defect.

2. Verified ground truth

Read from the decompiled game at necesse\engine\loading\ServerLoader.java (handleLaunchArgs, plus the option reads in loadGame), not from documentation or memory.

This is every option this feature exposes. ServerLoader reads four more that it deliberately does not: world, datadir and nogui belong to the daemon (§5), and settings and logs are excluded for the reasons given there. Options handled further up in GameLaunch rather than by the server loader - dev, lowmemory, hiddencheats and similar - are outside this feature entirely.

OptionTypeThe game's own handling

Two properties of that table matter more than the individual rows. The game clamps rather than rejects, and an unparseable integer only logs a warning and keeps the default. So a wrong value never fails a launch - it quietly becomes a different value. And because the parser is a map, a duplicated flag silently keeps the last occurrence, which is the exact mechanism behind the owner bug.

3. Decisions taken

QuestionDecisionConsequence
ScopePer world, with daemon-wide defaults A world sets only what it wants to differ; the rest is inherited. Costs a merge at launch and a UI that distinguishes inherited from overridden.
OwnerA per-world option like any other DaemonConfig.owners: string[] is retired. Different worlds can have different owners, which is the thing that could not be expressed before.
CoverageAll options, grouped One schema drives the form, so twenty fields cost about what six would. Nothing has to be added later when a rarely-used option turns out to matter.
ValidationIn the daemon, at save time The value shown in the UI is the value that runs. Rejects what the game would silently clamp.

4. Model and storage

A new launch-options.json in the state directory, shaped like mod-sets.json because that file already solves per-world storage:

{
  "defaults": { "owner": "Jeff", "slots": 5 },
  "worlds": {
    "Tulsa": { "motd": "Tulsa server", "pausewhenempty": true }
  },
  "updatedAt": "2026-07-31T00:00:00.000Z"
}

Defaults live here rather than in config.json: that file is about where things are, this one is about how the game runs. Effective options for a launch are defaults merged with that world's overrides. An option set in neither is not passed at all, so the game applies its own default rather than the daemon guessing at one.

launch-options-schema.ts is the single source of truth for the option set: CLI name, type, group, label, and the game's constraint. It mirrors world-settings-schema.ts, which already drives a typed form from a schema, so the client form is generated rather than hand-written.

Groups, for the UI only: Identity (owner, motd, password), Capacity (slots, port, ip), Behaviour (pausewhenempty, strictserverauthority, zipsaves, logging), World (worldborder, itemslife, unloadlevels, unloadsettlements, maxsettlements, maxsettlers, language).

5. The boundary that must not move

-nogui, -datadir and -world stay daemon-controlled and are not in the schema, so they cannot be set or overridden through any path.

-datadir is the one that would be catastrophic. It is the entire reason the daemon can run as SYSTEM and still find the real worlds and mods: without it the game derives those folders from the running account, and as SYSTEM that is a profile directory containing nothing. A user-supplied value would produce a server that starts cleanly, loads zero worlds and zero mods, and reports a completely successful launch. That is the worst failure shape in this codebase, and the schema's omission is what prevents it.

-settings is excluded for a different reason: it loads a settings file whose values handleLaunchArgs then overrides, so allowing both would create two sources of truth with a non-obvious precedence. -logs is excluded because it relocates the game's log directory, and the daemon reads the game's output from the process rather than from disk - moving it would change nothing the operator can see through this app while quietly breaking the assumption that logs sit under the data directory.

6. Migration

config.json's owners array becomes defaults.owner, taking the first entry (trimmed). It is removed from ALLOWED_CONFIG_KEYS in http.ts, so nothing can set it any more. No per-world overrides are created: every world inherits the default until one is deliberately overridden.

owners is NOT dropped from the config file. loadConfig and saveConfig round-trip every key they do not explicitly derive, so the array stays in config.json forever and is still readable at every later boot. That is why the migration's re-run guard cannot be "a default owner exists": an operator who deliberately cleared the owner would have had it re-seeded from the stale array at the next daemon start, silently. The guard is a durable ownersMigratedAt marker in launch-options.json instead, so the migration runs at most once whatever the current state is. An install that already had an owner when the marker was introduced is recorded as migrated and left untouched.

This changes behaviour on the existing install, deliberately and by the owner's decision. The server currently applies Eli, because the last -owner wins. Seeding the first entry means the next start of any world moves owner permissions to Jeff. That is the fix the feature exists to deliver, but it happens at the next start, not when the UI is next opened, so the daemon logs once what it migrated and which name it kept.

7. Validation

Values are validated in the daemon when saved, against the same bounds §2 records, and an out-of-range value is refused with a message naming the game's limit. It is not passed through for the game to clamp.

The reason is the failure mode, not tidiness: the game clamps silently. Type 300 into a slots field that forwards blindly, and the UI shows 300, the server runs 250, and the only evidence is a line in a log nobody reads. Refusing at save time is what keeps the number on screen and the number in effect the same number. world-settings-schema.ts's checkChange already sets this precedent.

Booleans are emitted as true/false. That is correct for every boolean option including zipsaves and unloadsettlements, which treat anything that is not 1/true as false.

8. API and client

RouteBehaviour
GET /api/worlds/:world/launch-options Returns effective, overrides, defaults and the schema. The schema is served rather than duplicated into the client: types.ts is already a byte-identical duplicate and one such file is enough to keep in step.
PUT /api/worlds/:world/launch-options A partial set of changes. An explicit null clears an override so the field falls back to the default.
GET / PUT /api/launch-options/defaults The daemon-wide set, same validation.

buildArgs becomes a pure function of the config, the world and the effective options, emitting -name value only for options that are set. Iterating a record guarantees each flag appears at most once, which matters because a duplicate would silently win - the mechanism behind the original bug.

The client gets a dialog in the style of WorldSettingsDialog, opened from the same place, with the four groups. Inherited values render muted with an "inherited from defaults" marker and a control to override; overridden values get "revert to default".

Editing is allowed at any time, because it only writes a JSON file. Changes take effect at that world's next start, since the game reads its arguments once. If the server is currently running that world the dialog says so, rather than implying the change is already live.

One warning belongs in the UI, not only the docs. port here is the game port, not the daemon's. The firewall rule register-task.ps1 creates covers the daemon's port only. Change the game port and players can reach nothing until a matching rule exists - while the daemon continues to look perfectly healthy, because its own port still answers.

9. Testing

Beyond schema bounds and merge behaviour, two tests carry the weight:

  • The daemon's own arguments cannot be overridden. Feed buildArgs an overrides record that tries to set datadir, world and nogui, and assert the emitted array still carries the daemon's values, exactly once each. A regression here produces a server that starts successfully with nothing in it.
  • The migration seeds the intended owner. From a config with owners: ["Jeff", "Eli"], assert defaults.owner === "Jeff" and that no per-world override is created.

Also: each numeric bound refused at its edge with the limit named; an unset option absent from the argument list entirely rather than emitted empty; an override beating a default and an unset field falling through to it; and a seam test in client/test/api.integration.test.ts that PUTs overrides and GETs them back through the real client transport, since that is the only place a real request crosses a real socket.

10. Out of scope

  • Applying changes to a running server. The game reads its arguments once at startup; there is no live reload to build.
  • -settings file support. Excluded for the precedence reason in §5.
  • Opening a firewall rule for a changed game port. Warned about, not automated: the daemon does not manage the game's own port today and making it do so is a separate decision.
  • Changes to worldSettings.cfg or its editor. That file holds the world's own rules and is a different concern that already has a working editor.
