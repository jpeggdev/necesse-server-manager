Player tracking and server commands

Design, 2026-08-01. Necesse Server Manager.

What this adds

Two features that share a seam. A players panel showing who is on the server right now, derived from the console output the daemon already streams. And a way to send the game's own commands from the client, as generated forms rather than a text box.

They meet at one point: the game's "online player" parameter type becomes a dropdown fed by the live roster, so /kick, /give and /tp pick from real names instead of asking the operator to type one correctly.

Ground truth

Everything below was read out of the game rather than the wiki. The decompiled tree in necesse-projects/decompiled is 1.2.0 while the server runs 1.3.1, so the formats are treated as a starting point and the implementation captures real 1.3.1 output as fixtures before trusting any parser.

Lines the server prints

EventLineSource
Connecting Client "<auth>" with address <addr> is connecting with version <v>. Server.addClient
Connected Client <consoleName> connected on slot <n>/<slots>. Server.addClient
New player Creating new player: <auth> Server.addClient
Clean quit Player <auth> ("<name>") disconnected with message: <reason> PacketDisconnect.processServer
Timeout Resetting connection for "<name>" due to no packets received for <ms> ms. ServerClient
Latency kick Ping threshold for "<name>" reached, resulting in kick. Limit is <n> seconds. ServerClient

The disconnect line is not universal. Player <auth> ("<name>") disconnected with message: Quit is printed by PacketDisconnect.processServer, and only on a clean CLIENT_DISCONNECT. Every other way a player leaves reaches Server.disconnectClient directly, which prints nothing per player: timeouts, latency kicks, /kick, missing appearance, and server shutdown. A roster built only by matching connects to that one line will hold ghosts after a crash-out. This is the single fact that shapes the design.

The console name is not always a name

In Server.addClient, consoleName is the stored player name only when the world already knows that authentication. For a first-time player it is the numeric auth. So connected on slot cannot be relied on for the display name, and the auth is the only identifier present on both the connect and the disconnect lines. The roster is keyed by auth.

/players is a complete snapshot

Run from the console (serverClient == null), the command prints the plain name rather than a teleport parse string:

Players online: 2/5
Slot 1: 76561198048435182 "Jeff", latency: 42, level: surface,conn: 1.2.3.4:5678
Slot 2: 76561198000000000 "eli", latency: 31, level: cave,conn: 1.2.3.5:5678

Auth, name, slot, latency and level in one place. This is the authority the event parsing is checked against, and the only source of latency and level.

Every command has a machine-readable definition

All 90 classes in necesse/engine/commands/serverCommands extend ModularChatCommand. None hand-parse their arguments.

ModularChatCommand(String name, String action, PermissionLevel level,
                   boolean isCheat, CmdParameter... parameters)

CmdParameter(String name, ParameterHandler<?> handler, boolean optional,
             boolean partOfUsage, CmdParameter... extraParams)

For example GiveServerCommand:

super("give", "Gives item to player", PermissionLevel.ADMIN, true,
      new CmdParameter("player", new ServerClientParameterHandler(true, false), true),
      new CmdParameter("item",   new ItemParameterHandler()),
      new CmdParameter("amount", new IntParameterHandler(1), true));

Name, description, permission level, cheat flag, and per-parameter type and optionality. The wiki's "(cheats)" annotations are this isCheat boolean. There are 26 parameter handler types.

Decisions taken

DecisionWhy
Live roster only. No history, playtime or persistence. No new state file, nothing to migrate, and the roster is a fact about a running process. It empties when the server stops.
Roster keyed by authentication, not name. The auth is on both the connect and disconnect lines; the name is not reliably on the connect side for a first-time player.
Console events for immediacy, /players for truth. Events show a join the moment it happens. /players is the server stating its own roster, which is what clears a ghost.
Reconcile on events, never on a timer. Each /players writes its output to the console panel the operator is reading. Triggered on server ready, on an unattributable disconnect line, and on an explicit Refresh.
A generated form per command, for all 90. Chosen over a raw command box. The definitions are already structured, so the forms can be too.
Schema extracted from SERVER's Server.jar, checked in. The artifact that will receive the commands, not the workstation's Necesse.jar and not the wiki. One source of truth, in the spirit of LAUNCH_OPTION_FIELDS.
The API takes a command name and named arguments, never a raw line. A raw string endpoint is arbitrary command execution on the game server, behind a token that is allowed to be empty. Structured input means the daemon can only emit commands that exist.
/stop, /exit, /quit are excluded. The daemon owns the lifecycle and its stop deliberately never escalates to a kill. Same reasoning that keeps nogui, datadir and world out of launch options.
Irreversible commands require a typed confirmation. /allowcheats is documented as not reversible; /regen rewrites a level; /deleteplayer removes player files. One click should not reach them.
Player-context commands are hidden. /die, /me, /copyitem and /reveal with no target act on the caller. There is no caller when the console sends them.
Roster ships as its own WebSocket message, not inside StatusPayload. Status is pushed on state changes; the roster changes on different ones. Merging them repaints the header on every join.
Players panel is a tab beside Mods. Neither list is squeezed and the console keeps its full height.

Architecture

Daemon

  • src/player-roster.ts - the roster and its parsers. Subscribes to ProcessManager's existing "line" event, so it adds no new plumbing. Holds a Map keyed by auth. Cleared whenever the process exits.
  • src/server-commands-schema.ts - the generated, checked-in command table plus the policy flags. The single source of truth for what may be sent.
  • src/process-manager.ts - gains send(command: string), which writes one line to the child's stdin exactly as the existing stop path does, and refuses on the two cases stop already handles.
  • src/http.ts - GET /api/players, POST /api/players/refresh, GET /api/commands (the schema the client renders forms from), and POST /api/command.
  • src/types.ts - PlayerEntry, CommandDef, CommandParam, and a players member on WsMessage. Copied byte-identical into the client.

Client

  • src/PlayersPanel.tsx - the roster list and a Refresh control, in a tab strip with the existing mods panel.
  • src/CommandDialog.tsx - command picker, generated fields, and the typed confirmation for destructive commands. Dialogs are how this app does form-heavy work already.
  • src/useDaemon.ts - handles the new players message.

Data flow

game stdout
  -> ProcessManager ingest (splits lines, strips nothing)
  -> "line" event
       -> existing console broadcast  (unchanged)
       -> PlayerRoster.observe(line)  (new)
            -> roster changed? broadcast { type: "players", players: [...] }

client form submit
  -> POST /api/command { name, args }
  -> validate against schema, render one line, ProcessManager.send
  -> game prints its CommandLog to stdout, which is already streaming back

The roster

Entry shape

interface PlayerEntry {
  auth: string;          // the join key, present on both connect and disconnect
  name: string;          // "" until known
  slot: number | null;
  latency: number | null;   // only from /players
  level: string | null;     // only from /players
  joinedAt: string | null;  // null when the daemon did not see the join
}

What opens and closes an entry

  • Opens: the is connecting with version line, keyed by its auth. The connected on slot line then fills in the slot, and the name if it was a name rather than an auth.
  • Closes by auth: the disconnected with message line.
  • Closes by name: the timeout and latency-kick lines, which carry only a quoted name. If no entry matches that name, the line is treated as an unattributable disconnect and triggers a /players reconcile.
  • Replaced wholesale: a parsed /players block. This is the only path that sets latency and level.
  • Emptied: process exit, for any reason.

Session duration is only shown when the daemon saw the join. A player discovered through /players (daemon restarted against a running server, or a missed connect line) has no join time. That row shows a dash. The alternative, dating it from daemon start, would be a number the operator would reasonably read as playtime and it would be wrong.

Sending commands

Request

POST /api/command
{ "name": "give", "args": { "player": "eli", "item": "iron_bar", "amount": 10 } }

The daemon looks the name up in the schema, checks each argument against its parameter type, renders /give eli iron_bar 10, and writes it. The client never composes the line.

Validation, in order

  1. The server is running and was spawned by this daemon. An adopted process has no stdin pipe, the same reason stop already gives.
  2. The command exists in the schema and is not excluded. An excluded command is absent from the table, so this is a lookup failure rather than a special case.
  3. Every required parameter is present, and no unknown argument is supplied.
  4. No argument contains a newline, carriage return or tab.
  5. Typed arguments parse: int, float and bool are checked; registry-backed values are passed through for the game to accept or reject.

Rule 4 is the security-relevant one. stdin is line-oriented, so a value containing a newline smuggles a second command onto the wire: /say hello\n/allowcheats would run both. This is the same class of defect as the launch-option values that re-parsed as flags, and it gets the same treatment: rejected at the boundary, with a test that feeds a real control character through and fails when the guard is removed.

Output

No new channel. The game prints its CommandLog to stdout, which already streams to the console panel. The daemon echoes the line it sent immediately before sending it, so the console reads as a transcript of what was run and what came back.

Schema extraction

  1. Copy C:\necesseserver\Server.jar from SERVER to the scratchpad. That is the artifact that receives these commands. The workstation's Necesse.jar is a different build.
  2. Run CFR over it once into the scratchpad, filtered to necesse.engine.commands.*.
  3. Parse the single super(...) call in each *ServerCommand.java into a schema entry: name, description, permission level, isCheat, and each parameter's name, handler type and optionality.
  4. Apply the policy flags: excluded for the three lifecycle commands, destructive for the irreversible ones, playerOnly for the ones that act on the caller.
  5. Emit daemon/src/server-commands-schema.ts, and record the game version it came from in the same file.
  6. Verify by sending /help to the live server once and diffing the command names it reports against the schema.

Parameter types to form controls

GroupHandlersControl
Enumerable Bool, Enum, PermissionLevel Select with the real values
Numeric Int, Float, RelativeInt Number input, seeded with the handler's own default
Online player ServerClient Select fed by the live roster
Registry-backed Item, Buff, Enchantment, Biome, Tile, Team, Settler, StoredPlayer, and the rest Free text. Their valid values are game registries that cannot be listed statically; the server rejects a bad one and says why

The schema is about the game's version, not ours. A game update can add or change commands, leaving a checked-in schema quietly wrong. GET /api/status already reports the running server's gameVersion, so the daemon compares it against the version stamped in the schema and surfaces a warning when they differ. Offering a command that no longer exists is a worse failure than saying the table may be stale.

Errors

Consistent with the rest of this daemon: nothing is swallowed, and a failure says what to do about it.

  • Server not running, or running but not ours: refused with the same distinction stop already draws.
  • Unknown or excluded command: 400 naming the command.
  • Bad argument: 400 naming the parameter and what was wrong with it.
  • A /players reconcile that produces no parseable block: the roster is left as it was and the failure is reported, rather than silently emptying the panel.

Testing

Fixtures must be captured, not composed. This repo already treats daemon/test/fixtures/log-fixtures.ts as evidence, because the game emits ANSI colour before the timestamp and that broke shutdown detection while every unit test passed. The connect, disconnect and /players lines get the same treatment: captured verbatim from a real 1.3.1 session before any parser is trusted. That needs a couple of minutes of the operator joining and quitting a world during implementation.

  • Parsers run on normalised lines and are tested with the ANSI prefix present.
  • The roster is tested as a sequence: connect, connect, unattributable disconnect, reconcile. Including the first-time-player case where connected on slot carries an auth rather than a name.
  • An argument containing a newline is rejected. An excluded command cannot be sent by name. Both proved by deleting the guard and confirming red.
  • ProcessManager.send refuses on a stopped server and on an adopted one.
  • A seam test in client/test/api.integration.test.ts drives POST /api/command through the real client transport against a real daemon. New shapes crossing the wire are exactly why that file exists.
  • Daemon sources stay ES2020-compatible, since the client typechecks them a second time.
  • daemon/src/types.ts and client/src/types.ts hashed after editing.

Out of scope

  • Playtime, session history, last-seen, or any persistence of who was on.
  • A raw command box. The forms are the interface.
  • Chat relay, or reading player chat out of the console.
  • Client-side autocomplete of item, buff or biome identifiers.
  • Anything that changes how the daemon starts or stops the server.

Known limits

  • A ghost survives until the next reconcile trigger or a manual Refresh. This is the accepted cost of not polling.
  • The schema is a snapshot of one game version and is only as current as its last extraction. The version warning makes that visible rather than silent.
  • Registry-backed arguments are validated by the game, not by the form, so a typo is reported after sending rather than before.
