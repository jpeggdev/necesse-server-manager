Update All: skip unchanged mods

Design, 2026-07-31. Necesse Server Manager.

The problem

ModInstaller.updateAll loops every managed mod and calls install unconditionally: a steamcmd download, a jar copy, a library write and a registry upsert, per mod, every time. With 11 managed mods that is 11 full downloads to land however many actual updates exist, usually zero.

The comparison that would prevent this already exists and is careful, but it lives only in GET /api/mods/updates, which paints the update badges. It never gates the loop.

Decisions taken

QuestionDecisionWhy
Is a moved time_updated good enough evidence? Yes, trust it. Steam moves time_updated for any edit to the entry, including a retitle or a new screenshot. It indicates a new jar rather than proving one. Accepted: the cost of a false positive is one unnecessary download.
What happens when we cannot tell? Reinstall. Unknown means might have changed. Never silently miss an update. This covers a mod with no workshop entry, a null time_updated, and an unreadable stored value.
What if Steam is unreachable entirely? Reinstall everything, and say so. Falls out of the rule above: every mod becomes unknown. That is exactly today's behaviour, so an outage costs speed and nothing else. No abort.
Compare against what? Steam's timestamp to Steam's timestamp. See below. Comparing Steam's clock to ours has two failure modes.
A force-reinstall-everything switch? No. YAGNI. The gate reinstalls anything unknown or missing, which covers the real repair cases, and POST /api/mods already reinstalls a single mod by id.

Why not compare against install time

ModEntry.lastUpdated is the wall-clock time this daemon performed the install, not anything Steam said. Gating on workshopUpdatedAt > lastUpdated therefore compares two different clocks, and fails in two ways:

  • If this box's clock and Steam's disagree, the comparison is wrong in one direction or the other for every mod at once.
  • If a mod is republished while we are downloading it, we record an install time later than the new time_updated, conclude we are current, and keep the older jar. Nothing ever corrects it.

Storing the value Steam gave us removes both.

Data model

ModEntry gains one field, in both daemon/src/types.ts and client/src/types.ts, which stay byte-identical:

/**
 * The workshop entry's `time_updated`, as ISO, for the jar currently
 * installed. `null` when unknown: written by a daemon that predates this
 * field, or installed while Steam could not be reached.
 */
workshopUpdatedAt: string | null;
This field is also the migration. Every entry written before it existed reads as null, which is unknown, which reinstalls. So the first Update All after this ships behaves exactly like today, and every run after it is gated. There is no migration code to write and nothing to get wrong.

The gate

A mod is skipped only if all five conditions hold. Anything else reinstalls.

#ConditionFailing it means
1Steam returned an entry for this idDelisted, private, or an id that no longer resolves
2That entry has a usable time_updatedSteam answered but without the field we gate on
3The registry's workshopUpdatedAt is not nullWe never recorded what we installed
4The two values are equalThe entry changed since we installed it
5The library still resolves a current jar for itThe jar is gone, so there is nothing to keep

Condition 4 is equality rather than > deliberately. Any movement in Steam's timestamp means the entry is not the one we installed, including movement backwards, which a > test would skip in silence.

Condition 5 is what makes a hand-deleted or lost jar self-heal. Without it a mod with correct timestamps and no jar is skipped forever as "current".

To pin down during planning: condition 5 is ModLibrary.resolve(id), but the library keys entries by its own ModLibraryEntry.id while a managed mod is keyed by its workshop published-file id, and library.add is handed the workshop id inside a ModSource. Confirm those are the same keyspace before relying on the lookup. If they are not, the condition needs the workshop-id lookup instead, and a test that a jar removed from the library forces a reinstall would otherwise pass for the wrong reason.

Flow

  1. registry.load() for the managed list.
  2. One workshop.getDetails(ids) call for the whole run. On throw: log the failure with its message, treat every mod as unknown, continue.
  3. Per mod, evaluate the five conditions. Skip, or install.
  4. install() records the entry's time_updated into the registry alongside the jar it wrote.

install() signature

install takes the timestamp as a parameter rather than fetching its own, so updateAll pays for one Steam call and not one per mod. POST /api/mods fetches details for its single id and passes the value through, so a fresh install is exact immediately. If that fetch fails the install still proceeds with null, and the next Update All corrects it once.

One comparison, two callers

The badge and the gate must not be able to disagree. Today the badge route compares workshopUpdatedAt > installTime. If the gate moves to the stored-Steam-value basis and the badge does not, the client shows "update available" on a mod that Update All then skips. Both look correct in isolation, which is what makes it hard to diagnose.

So the comparison becomes one exported function, and both GET /api/mods/updates and updateAll call it. ModUpdateInfo.installedAt keeps reporting this daemon's install time, because that is genuinely what it means to someone reading the UI; only the decision changes basis.

Reporting

InstallResult gains skipped?: boolean, matching the existing optional replacedJar?. A skipped mod is ok: true, skipped: true, carrying its existing jar.

The streamed run log distinguishes the two cases per mod, and closes with a summary line:

--- Updating <name> (<id>)
--- <name> (<id>) is unchanged, skipping
...
Updated 2, skipped 9, failed 0.

The client must render a skipped mod as skipped. Counting them as updates would have the run claim 11 updates for 2 downloads, which is worse than the unconditional behaviour it replaces.

Errors

Unchanged from the rest of the daemon: nothing is swallowed or reworded.

  • A per-mod install failure records ok: false with its message and the loop continues, as it does today.
  • The getDetails failure is written to the run log with its message and degrades to reinstall-everything. It is not silently treated as "no updates", which is the one answer that would be actively misleading.

Testing

The gate has five clauses, so a single all-conditions-true test would pass trivially against a broken implementation. Required:

  • The central test: a fully current mod is never handed to steamcmd. This is the substitution target - delete the gate and it must go red.
  • One test per clause, flipping only that condition and asserting a download happens. Five tests, not one.
  • The recorded workshopUpdatedAt is Steam's value, not this machine's clock.
  • getDetails throwing downloads everything and puts the reason in the log.
  • The badge and the gate agree: a mod the gate would skip does not show as having an update available.
  • One seam test in client/test/api.integration.test.ts, since skipped is a new shape crossing the wire and the client's mocked tests cannot see it.

Existing updateAll tests assume unconditional reinstall. Several will need a stored timestamp to keep asserting what they were written to assert; that churn is expected rather than a sign something is wrong.

Out of scope

  • A force-reinstall switch.
  • Verifying the downloaded jar actually differs. Steam gives us an entry timestamp, not a file hash, and hashing after the fact would mean doing the download we are trying to avoid.
  • Changing what a mod set stores. Sets reference mod identity, not a jar version; Update All refreshes the library and each world picks the new version up at its next start.
Supersedes nothing. Related: docs/mod-sets-design.md decision row 1.
