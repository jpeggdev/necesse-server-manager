1. Goal & scope

A desktop app on the workstation that manages the Necesse dedicated server running on a separate machine (SERVER, 192.168.1.106) over the LAN. It must start and stop the server, launch or create worlds by name, update the server binaries, manage the installed mod set by Steam Workshop id, and stream the server console live. Errors surface verbatim rather than as generic failures.

Success criteria

  • Start a named world from the client; the console streams until the server reports ready.
  • Typing a world name that does not exist creates it, and the UI says so before launch.
  • Stop performs a graceful save-and-shutdown, not a process kill.
  • Adding a mod by workshop id downloads and installs it, replacing any prior jar for that id.
  • Update All refreshes every managed mod and reports per-mod outcome.
  • Any failure shows the underlying tool's own output.

2. Verified ground truth

Every path below was read off SERVER over SSH on 2026-07-26, not assumed. The placeholder paths in the existing Update-Necesse.ps1 (C:\steamcmd, C:\Servers\Necesse) do not exist.

The real launch line

Taken from latest-server-log.txt:

-nogui -world "Infected Toenail" -owner Jeff -owner Eli

The -owner flags grant owner permissions to any client connecting under that name. They are configuration, not hardcoded, and are passed on every start.

3. Architecture

Two deliverables in one repo.

Daemon Node + TypeScript, runs on SERVER

Owns all state and every side effect. Listens on port 8710 for HTTP and WebSocket. No authentication — the LAN is trusted, a deliberate choice recorded here because this API can stop processes and delete files.

Client Tauri 2 + React/TS, runs on the workstation

A thin shell around a web UI. No Rust logic beyond window creation; all calls go from the webview to the daemon over HTTP and one WebSocket. The client holds no authoritative state, so closing it never affects the running game server, and a second client would see identical state.

Each module has one purpose, a narrow interface, and injected dependencies so it is testable without a Necesse install.

4. Process lifecycle

Why the daemon must own the process. On Windows you cannot write to the stdin of a process you did not create. "Find the java process and send stop" is therefore impossible for a server started by anything else. The daemon spawns the server itself and holds the pipe for its lifetime.

Start

Working directory must be the server root, since the server resolves its root path from cwd.

cwd: C:\necesseserver
C:\necesseserver\jre\bin\java.exe
  -XX:+UnlockExperimentalVMOptions -XX:+UseG1GC -XX:+ExplicitGCInvokesConcurrent
  -XX:G1NewSizePercent=20 -XX:G1ReservePercent=20 -XX:MaxGCPauseMillis=50
  -XX:G1HeapRegionSize=32M
  -jar Server.jar -nogui -world "<name>" -owner Jeff -owner Eli

State machine

States are driven by real log strings captured from the server's own output, not by guesses or timers.

StateEntered when
stoppedNo child process.
startingChild spawned. Mod loading happens here and can take tens of seconds.
runningA line matches /^Started server using port (\d+) with (\d+) slots on world "(.+?)"/.
stoppingstop\n written to stdin.
unmanagedA Necesse java process exists that this daemon did not spawn.
crashedChild exited with a nonzero code without passing through stopping.
Log strings this design relies on 
Loading existing world at ...\saves\worlds\Infected Toenail.zip
Started server using port 14159 with 5 slots on world "Infected Toenail.zip", game version 1.2.0.
Local address: 192.168.1.106:14159
> stop
Completed world save before stopping server
Server has stopped

Loading existing world confirms after the fact whether a world was loaded or newly created, which the client displays so a typo that created a world is immediately visible.

Stop

Write stop\n to stdin, then wait for exit with a 90-second timeout. The server saves the world before exiting, so this must never be shortcut. On timeout the daemon reports that the process did not exit and offers a kill as an explicit, separately confirmed action — it never escalates on its own.

The unmanaged case

On startup the daemon scans for a running java.exe whose command line references Server.jar. If found, state is unmanaged: the client shows that the server is up but not controllable, and the only offered action is a hard kill labelled as risking world loss. The daemon does not pretend it can stop it gracefully.

5. Mod management

The problem with the current script

Update-Necesse.ps1 copies every jar it finds into the mods folder. When a mod's version is in its filename — SafeHavenQOL-1.2.0-2.6.jar → -2.7.jar — the old jar stays behind and the server loads the mod twice. The registry exists to fix exactly this.

mods.json

[
  { "id": "3731244177", "name": "Safe Haven QOL",
    "jar": "SafeHavenQOL-1.2.0-2.6.jar", "lastUpdated": "2026-07-26T04:24:00Z" }
]

Install / update one mod

steamcmd +login anonymous +workshop_download_item 1169040 <id> +quit
  → C:\Users\jeffp\steam\steamapps\workshop\content\1169040\<id>\*.jar
  1. Run steamcmd, streaming its output to the client as a task.
  2. Locate the downloaded jar. If the folder holds no jar, fail with steamcmd's output attached.
  3. Copy it into the mods dir.
  4. If the registry recorded a different jar name for this id, delete that old jar.
  5. Write the registry entry.

Update All runs this per managed mod and reports each outcome individually — updated, already current, or failed with its error. One mod failing never aborts the rest.

Untracked jars

Any jar in the mods folder with no registry entry is listed as untracked: removable, but not updatable, and labelled as such. Adding a workshop id whose download produces a matching filename adopts that jar into the registry. Nothing is ever guessed into managed state.

modlist.data in the mods folder is Necesse's own enable/disable record, keyed by internal mod id rather than workshop id. The daemon does not write it; the server regenerates it. Mod enable/disable is out of scope for this version.

Mods change only while stopped

The server reads its mod set once at startup. Mod mutations are refused while the server is running, with a message saying so, rather than silently taking effect at some unpredictable later point.

6. Server updates

steamcmd +force_install_dir C:\necesseserver +login anonymous
         +app_update 1169370 validate +quit

Anonymous, no credentials, because the dedicated server is a separate free app from the game. Output streams to the client as a task. If the server is running the request is refused with a clear message rather than shutting the game down as a side effect — stopping is the operator's decision.

GET /api/config / PUT /api/configRead and edit owners, paths, JVM args.

WebSocket messages

  • console — one server output line.
  • status — a state transition with the new status payload.
  • task — streamed output from a steamcmd operation, terminating in success or an error.

On connect the client receives the ring buffer as backlog, so a client opened mid-session sees recent history rather than an empty console.

8. Client UI

A single window, three regions.

Header

Status pill, world input, Start / Stop, Update Server.

The world input is a free-text combobox, not a picker. Existing worlds appear as suggestions and the field is prefilled with lastWorld, but any typed name is passed straight through to -world. Because that creates a world when the name is unknown, the field shows a live indicator — "will load existing world" or "will create a new world" — so a typo is caught before launch rather than discovered as a mystery empty world afterwards.

Mods panel

Rows show name, workshop id, installed jar, and an X to remove. Untracked rows are visually distinct and lack an update affordance. Below the list, an add row taking id and name, and Update All. While the server is running the mutation controls are disabled with the reason shown.

Console

Live output with autoscroll that disengages when scrolled up and resumes on return to the bottom. Task output from steamcmd is interleaved and visually distinguished from game output.

9. Error handling

Nothing is swallowed or reworded. Every route resolves to a result or {ok: false, error} carrying the underlying message — steamcmd's stderr, the spawn ENOENT, the missing jar. The client renders that text in a dismissible banner.

Failures that must be distinguishable rather than collapsed into "failed":

  • steamcmd missing at the configured path, versus steamcmd running and failing.
  • Workshop download producing no jar, versus a copy failing.
  • Server exiting during starting — usually a bad mod — surfaced with the tail of the console, which is where the actual cause is.
  • Stop timing out, versus stop failing to write to stdin.
  • Daemon unreachable, distinguished by the client from an error returned by the daemon.

10. Testing

process-manager, mod-registry, mod-installer, and steamcmd receive spawn and their filesystem access as injected dependencies, so the full start / stop / install / update-all logic is unit-testable against a fake process emitting recorded log lines, with no Necesse install present.

Covered by unit tests: state transitions against real captured log output, stop timeout, the stale-jar replacement path, update-all continuing past a single mod's failure, and steamcmd argument construction.

Verification honesty. Unit tests exercise none of the real integration. Live verification runs against SERVER over SSH and must state which configuration was exercised: real start and stop of a real world, a real mod install, and a real app update. Anything not exercised — notably the unmanaged and crashed paths, which need a deliberately broken mod or an externally launched server — gets named explicitly as untested rather than implied covered by a green test run.

11. Deployment

  1. Install Node LTS on SERVER over SSH via winget.
  2. Copy the daemon to SERVER; write config.json with the verified paths and seed mods.json from the table above.
  3. Open port 8710 inbound on SERVER's firewall.
  4. Register a Scheduled Task to run the daemon at logon so the client can connect any time.
  5. Build the Tauri client on the workstation, pointed at 192.168.1.106:8710.

The Tauri webview must be allowed to reach the daemon's origin: the daemon sends permissive CORS headers and the client's CSP allows http://192.168.1.106:8710 for both HTTP and WebSocket.

12. Out of scope

  • Authentication — trusted LAN, chosen deliberately.
  • Arbitrary console commands; only stop is sent to stdin.
  • Player list and per-player admin actions.
  • Enabling/disabling mods without uninstalling (modlist.data is not written).
  • World backup, restore, and deletion.
  • Editing server.cfg (port, slots, password, MOTD).
  • Managing more than one server instance.
